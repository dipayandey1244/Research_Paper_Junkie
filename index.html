Step 1 of 8

“Best” hides the comparison criteria

“Best balloons for a birthday party” leaves the system to infer which qualities matter: color variety, durability, material, or age appropriateness. Word matching can retrieve balloons, but it cannot tell which relevant product is best for the implicit intent. Common IR benchmarks contain few superlative queries, so the paper builds a purpose-made product-search evaluation.

Relevant ≠ best

The paper’s corpus contains 21,407 superlative queries and 470k products. Query–product pairs carry three judgments: relevant and best, relevant but not best, or irrelevant.

✏️ If someone asks for the “best” balloon, ask yourself what makes one best for this party. The answer changes from one kind of product to another.
Step 2 of 8

Transfer large-model interpretation into compact hints

For each query, Claude 3.5 Sonnet v2 generates four offline hint blocks: a contextual explanation of the superlative, candidate brands, important features with synonyms, and ten feature-covering query reformulations. The hints are cached; the reasoning model is not called for every request.

Two distinct uses for hints
QE-BM25 uses the ten generated query variants plus suggested brands to expand sparse retrieval. For the best reranking result, reformulated queries and the top three brands are paired with each product and passed to a small pointwise model. The paper also ablates feature-text augmentation.
✏️ Let a knowledgeable helper write the judging clues once. A smaller, faster helper can reuse those clues for every product.
Step 3 of 8

Two experiments share a query understanding layer

A
Sparse retrieval. BM25 scores the original query. QE-BM25 separately scores ten reformulations, includes the suggested brands, and averages scores across variants. The paper also compares doc2query and a dense GTE-Qwen retriever.
B
Reranking. Use one shared first-stage retriever (GTE-Qwen2-7B) to fetch 50 candidates. A pointwise classifier scores each query–product pair. P is the query/product baseline; P+H uses generated query reformulations and the top three suggested brands; feature-text hints are a separate ablation.
C
Why pointwise? Fine-tuned Qwen2.5 0.5B and 3B rankers outperform the evaluated listwise 72B and reasoning-model baselines, with much smaller models. Each pair is classified as one of three relevance labels; the probability of “relevant and best” gives the ranking score.
Latency design: Hint generation and retrieval run concurrently. Hints can also be generated and cached offline; the paper reports the hint input adds 149 ms to 0.5B and 473 ms to 3B end-to-end latency in its setup.
Step 4 of 8

Implement the retrieval and ranking pieces

The local demo implements Okapi BM25 and the paper’s ten-variant score averaging. Its hint bundles use the same four fields, but are hand-authored for inspection. train_pointwise.py provides the actual Qwen sequence-classification fine-tuning path for a prepared CSV.

ranking_demo.py · QE-BM25
Python · BM25 
def qe_bm25(index, hints, max_candidates=50_000):
    total = Counter()
    for query in hints.generated_queries:  # ten reformulations
        text = query + " " + " ".join(hints.brands)
        scores = index.scores(text)
        top = sorted(((pid, score) for pid, score in scores.items() if score > 0),
                     key=lambda pair: (-pair[1], pair[0]))[:max_candidates]
        for product_id, score in top:
            total[product_id] += score / len(hints.generated_queries)
    return sorted(((p, total[p.product_id]) for p in index.products), key=lambda row: (-row[1], row[0].product_id))
What just happened?
Each generated query contributes its top nonzero BM25 matches. The score matrix averages across ten variants, treating a missing candidate score as zero; products with no match are omitted.

For labeled query q, reciprocal rank of the first relevant-and-best product is 1/rank (zero if missing). Hit@K is 1 when at least one relevant-and-best product is within the first K results. These metrics answer complementary questions:

$$\mathrm{MRR}=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{\mathrm{rank}_{best}(q)} \qquad \mathrm{Hit@K}=\frac{1}{|Q|}\sum_{q\in Q}\mathbf{1}[\mathrm{rank}_{best}(q)\le K]$$
Don’t compare unlike runs
Paper numbers use its custom test split and Claude-generated labels. Metrics from the local fixture are computed on two tiny invented queries. They demonstrate code behavior, not the reported benchmark.

Step 7 of 8

Data boundaries

✓
Underlying product source. The paper builds on the Amazon Shopping Queries dataset from the KDD Cup 2022, which is publicly documented.
✓
Paper’s derived evaluation set. Authors generated superlative queries by category, retrieved candidate products, and assigned three-way labels to 1.07M pairs (21,407 queries, 470k products; 13,914/2,140/5,353 train/dev/test queries).
!
Local implementation data. The paper’s derived annotations and cached LLM hints are not bundled here. The official code repository currently says it will be available soon. Our 12 products and 2 query judgments are authored examples only.
Reproducibility status: BM25 and QE-BM25 are implemented and runnable on the toy corpus. The Qwen pointwise P/P+H training path is implemented for prepared CSVs. We cannot claim the paper’s full benchmark reproduction without its derived query, hint, label files and the required model/GPU run.

Sources: Paper PDF · Authors’ code repository status · Amazon Shopping Queries KDD Cup.

Step 8 of 8

Fine-tune the pointwise model

Prepare a CSV with a query-group split and columns split, query_id, product_id, query, product_title, product_description, label. For query-based P+H, add hint_query, top_brands; create one row per reformulation/product pair, with the same original query_id and relevance label. The evaluator averages reformulation scores by product before ranking. Use | between brands. For the feature ablation use hint_features instead of hint_query.

The script uses the paper’s 1e-5 learning rate, early stopping on validation macro-F1, and batch size 32 for 0.5B (2 for 3B). It ranks each held-out query group by the predicted “relevant and best” probability, then reports MRR and Hit@K. The paper reports 3–4 hours on a single NVIDIA L40s for its fine-tuning runs; this local code has not been run on the paper dataset or weights.
